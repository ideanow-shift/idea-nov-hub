# Production Read-only Audit Runner: Human Approval Board

## 使い方

この資料は、本番データを変更しない監査を開始する前の承認用です。承認しても、この資料自体は接続・SQL実行・Role作成を起こしません。10件すべてが承認され、別途実行ゲートが発行されたときだけ、最初のカタログ限定監査を検討できます。

| ID | 決定内容 | 安全側の推奨 |
| --- | --- | --- |
| D01 | 本番同一性の照合 | private fingerprint の全一致 |
| D02 | 監査専用DB Role | 最小権限・RLS非迂回・1接続 |
| D03 | 固定10 Query | C01〜C10のみ |
| D04 | 結果形式 | sanitized schema v1のみ |
| D05 | 出力のマスキング | allowlist方式 |
| D06 | Query数 | 最大10、各1回 |
| D07 | 時間制限 | statement 5秒、lock 1秒、実行全体60秒 |
| D08 | 実行可能者 | 三者承認後にOS司令塔担当が実行 |
| D09 | 実行枠 | 1回・事前指定枠・失敗時は再承認 |
| D10 | 証跡と失効 | sanitized receiptのみ365日、資格情報は24時間以内に失効 |

## D01 Production Identity Profile

- **決定内容**: 本番であることを、生のhostやSecretを保存せず、project/database/host/organization・TLS・schema・extension・sentinel metadataのSHA-256 fingerprintで照合する。
- **推奨案**: すべてのfingerprintと環境名`production`が一致したときだけ接続する。1項目でも不一致・欠落ならquery 0件で停止する。
- **代替案**: host名などを手作業で照合する。
- **推奨理由**: 手入力や画面確認の見落としを減らし、接続値を成果物へ残さないため。
- **承認しない場合の影響**: 本番と確認できず、監査を安全に開始できない。
- **セキュリティリスク**: 誤った環境への接続。fingerprint自体もprivate profile外へ出さない。
- **運用負担**: Platform ownerとCore DB ownerによる初回照合・更新時再照合。
- **承認文**: 「D01のprivate fingerprint全一致方式を承認します。不一致時は接続およびQueryを0件で停止します。」
- **却下文**: 「D01を承認しません。本番read-only監査は開始しません。」
- **要修正文**: 「照合項目またはprofile管理責任者を明記して再提示してください。」

## D02 監査専用DB Role

- **決定内容**: 監査専用loginを用意し、承認済みの`public.stores`と`core.stores`へのSELECTと必要なcatalog可視性だけを与える。
- **推奨案**: `NOINHERIT`、`NOBYPASSRLS`、`NOEXECUTE`、書込み・DDL・TEMP・replicationなし、接続数1、search_path固定、資格情報は24時間以内に失効。
- **代替案**: 既存アプリRoleまたはservice roleを使う。
- **推奨理由**: 監査に不要な権限を持たず、RLSも迂回しないため。
- **承認しない場合の影響**: 安全な専用経路がなく、監査は実行不可。
- **セキュリティリスク**: SELECT権限には`COPY TO`相当の読み出しリスクが理論上あるため、資格情報をsealed runner以外へ渡さない。
- **運用負担**: DBAによる期限設定、実行後の失効確認、grantの棚卸し。
- **承認文**: 「D02の最小権限監査Role案を承認します。BYPASSRLS・継承・service role利用を認めません。」
- **却下文**: 「D02を承認しません。本番監査のDB接続は許可しません。」
- **要修正文**: 「対象relation、RLS結果、失効担当を追加して再提示してください。」

## D03 固定Query C01〜C10

- **決定内容**: 実行できるSQLは事前レビュー済みのC01〜C10だけに固定し、利用者はQuery ID以外のSQL、schema、テーブル、値を渡せない。
- **推奨案**: 最初の実行はC01〜C10のCore Master catalog確認に限定し、21店舗目の分類や状態別件数は別の承認枠で追加する。
- **代替案**: 12本を一度に実行する。
- **推奨理由**: 最初の接続は対象を最小化し、Role/RLS/結果形式を確かめられるため。
- **承認しない場合の影響**: 任意SQLを許容しない限り、監査は実行できない。
- **セキュリティリスク**: Queryの意図や出力項目の見落とし。各Queryは個別に承認記録へ残す。
- **運用負担**: Query追加・変更ごとに再レビューと再承認が必要。
- **承認文**: 「D03の固定10 Queryのみを承認します。任意SQL、RPC、export、再試行を認めません。」
- **却下文**: 「D03を承認しません。本番Queryは実行しません。」
- **要修正文**: 「該当Query ID、対象object、出力項目、停止条件を指定して再提示してください。」

## D04 Result Schema

- **決定内容**: 実行結果はrun ID、Query ID、件数、boolean、一致/不一致、固定失敗分類、rollback確認だけを含むschema v1へ固定する。
- **推奨案**: unknown fieldは拒否し、raw row・raw error・生UUID・会計金額・接続情報を出さない。
- **代替案**: 個別の監査目的ごとに自由形式の結果を出す。
- **推奨理由**: 証跡の比較ができ、余計な情報流出を防ぐため。
- **承認しない場合の影響**: 安全な証跡形式を保証できず、実行不可。
- **セキュリティリスク**: 便利さのために出力項目を増やすと機微情報が混じる。
- **運用負担**: schema変更はversionを上げ、再承認する。
- **承認文**: 「D04のsanitized result schema v1のみを承認します。」
- **却下文**: 「D04を承認しません。監査結果は保存・共有しません。」
- **要修正文**: 「必要な項目を固定キーとデータ分類で指定して再提示してください。」

## D05 Sanitization Policy

- **決定内容**: 出力をallowlistで制御し、許可されない項目を検出したらその結果を捨てて安全停止する。
- **推奨案**: 件数、true/false、schema/table/column名、policy名、masked UUID、sanitized timestampのみ許可する。
- **代替案**: 正規表現だけで後から伏せ字にする。
- **推奨理由**: 「許可されたものだけ出す」方が、未知の個人情報やSecretを漏らしにくいため。
- **承認しない場合の影響**: 監査結果を安全に保管・共有できない。
- **セキュリティリスク**: raw DB errorや新しい列が意図せず出力されること。
- **運用負担**: 新しい出力項目には分類・承認・テストを追加する。
- **承認文**: 「D05のallowlist sanitizationと、未許可項目発見時の安全停止を承認します。」
- **却下文**: 「D05を承認しません。結果を出力しないため監査は行いません。」
- **要修正文**: 「許可する項目と絶対に出さない項目を具体化して再提示してください。」

## D06 Query Count上限

- **決定内容**: 1実行で最大10 Query、同じQuery IDは1回だけとする。
- **推奨案**: 最大10、初回はC01〜C10の単発実行、失敗時の自動再実行なし。
- **代替案**: 必要に応じて回数を増やす。
- **推奨理由**: 負荷と調査範囲を予測可能にし、繰り返し実行を防ぐため。
- **承認しない場合の影響**: 実行上限がなくなり、意図しない負荷を説明できない。
- **セキュリティリスク**: 少量のQueryを繰り返して情報を集めること。
- **運用負担**: 13本目が必要な場合は新しいrun IDと再承認が必要。
- **承認文**: 「D06として1実行最大10 Query、各ID1回、自動再試行なしを承認します。」
- **却下文**: 「D06を承認しません。監査実行回数を定めないため開始しません。」
- **要修正文**: 「上限値、例外の有無、再承認条件を明記して再提示してください。」

## D07 Timeout設定

- **決定内容**: statement 5秒、lock 1秒、idle transaction 10秒、実行全体60秒を上限にする。
- **推奨案**: 上記の短い固定値を採用し、timeout時はrollbackして終了する。
- **代替案**: 調査に合わせて長いtimeoutを設定する。
- **推奨理由**: 監査が本番処理を待たせたり、長い接続を残したりしないため。
- **承認しない場合の影響**: 長時間Queryやロック待ちの抑止ができない。
- **セキュリティリスク**: timeout延長で負荷・障害影響が拡大すること。
- **運用負担**: timeoutしたQueryはSQL見直しと再承認が必要。
- **承認文**: 「D07の短時間timeoutと、timeout時のrollback・再承認制を承認します。」
- **却下文**: 「D07を承認しません。実行時間を制御できないため開始しません。」
- **要修正文**: 「対象Queryの必要性と影響評価を添えて再提示してください。」

## D08 実行可能者

- **決定内容**: 誰が実行を承認し、誰がsealed runnerを起動するかを分離する。
- **推奨案**: **C. 代表者＋OS責任者＋DB責任者の三者承認後に、OS司令塔担当が起動**。DB責任者は資格情報ブローカーを扱い、起動者と分離する。
- **代替案**: A. 代表者承認後にOS司令塔担当が実行、B. 代表者＋経理責任者の二者承認後に実行。
- **推奨理由**: 本番同一性、DB権限、事業目的を異なる責任者が確認できるため。
- **承認しない場合の影響**: 誰が責任を持つか不明確で、実行不可。
- **セキュリティリスク**: 1人で目的・権限・実行を完結させること。
- **運用負担**: 三者の時間調整が必要。ただし監査は例外的・低頻度のため妥当。
- **承認文**: 「D08として三者承認と起動者・資格情報担当の分離を承認します。」
- **却下文**: 「D08を承認しません。実行権限を付与しません。」
- **要修正文**: 「承認者、起動者、資格情報担当、代理時の扱いを指定して再提示してください。」

## D09 実行日時・実行枠

- **決定内容**: 監査目的、run ID、開始予定、終了予定、実行Queryを事前に固定する。
- **推奨案**: 業務影響の少ない時間に1回だけ、60秒以内、失敗時は原因レビュー後の再承認制とする。
- **代替案**: 必要時に都度、即時実行する。
- **推奨理由**: 実行の監督と異常時対応を可能にするため。
- **承認しない場合の影響**: 誰がいつ何を実行したかを統制できない。
- **セキュリティリスク**: 無制限の再実行や、障害時の実行。
- **運用負担**: 予定調整とrun ID発行が必要。
- **承認文**: 「D09として事前指定の単発実行枠と、失敗時の再承認制を承認します。」
- **却下文**: 「D09を承認しません。実行枠を発行しません。」
- **要修正文**: 「目的、対象Query、時間枠、停止条件を明記して再提示してください。」

## D10 証跡保管・資格情報失効

- **決定内容**: sanitized receiptのみを指定場所に365日保管し、資格情報は実行終了後、遅くとも24時間以内に失効・失効確認する。
- **推奨案**: Core DB governance配下のアクセス制限付き証跡庫に保存。閲覧者は代表者、OS責任者、DB責任者、監査担当に限定する。
- **代替案**: 個人PCやチャットへ結果を保存する。
- **推奨理由**: 監査可能性を保ちつつ、Secret・実UUID・実会計金額を残さないため。
- **承認しない場合の影響**: 実行後の説明責任と失効確認ができない。
- **セキュリティリスク**: 過剰なログ保管または資格情報の残存。
- **運用負担**: receipt登録、アクセス棚卸し、失効確認が必要。
- **承認文**: 「D10としてsanitized receiptの365日保管と、資格情報の24時間以内失効を承認します。」
- **却下文**: 「D10を承認しません。証跡保管と資格情報運用が整うまで実行しません。」
- **要修正文**: 「保管先、閲覧者、保存期間、失効担当を指定して再提示してください。」
