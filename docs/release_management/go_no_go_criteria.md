# Go / No-Go Criteria

## Go

以下を満たすときだけRelease Readyを判定できる。

1. データ整合性、業務フロー、UI/UX、実運用レビュー、開発品質がすべてPASS。
2. 各PASSに証拠と責任者がある。
3. 変更対象、対象利用者、対象データ期間、開始日時、問い合わせ先、rollback責任者が記録されている。
4. Production依存がある場合は、その依存ごとの個別承認・read-only/write境界を満たしている。

## No-Go

次のどれかがあれば正式運用開始をしない。

| 条件 | 判定 | 例 |
| --- | --- | --- |
| データ未整合・未確認 | NO_GO | Talentのデータ未投入、Store master SSoT未確定 |
| 業務フロー未確定 | NO_GO | 例外時に誰が判断・修正するか決まっていない |
| UIが状態を誤認させる | NO_GO | 未接続APIを利用可能に見せる |
| 対象部門レビュー未完了 | NO_GO | Store Operationsの営業部レビューが未実施 |
| 開発品質未達 | NO_GO | 必須テスト不合格、secret露出、rollback不能 |
| 条件付きのみ | NOT_READY | 期限付き承認、保留された重要論点 |

## Release 1.0 / 1.1の適用

- **1.0**: ローカル・UI・ガバナンス領域であっても、利用部門へ正式運用開始を案内するなら5条件が必要。単なる表示公開は`RELEASED`と混同しない。
- **1.1**: production read-only/API連携は、5条件に加えて個別のCore DB/API/Accounting/Talent承認とsmoke evidenceが必要。

## 判定会議の最小参加者

- 業務責任者
- データ責任者
- プロダクト/運用責任者
- 開発・セキュリティ責任者

経営判断が必要な場合は代表者が最終Go/No-Goを記録する。技術チームは、未確認事項をPASSとして代替判定しない。
